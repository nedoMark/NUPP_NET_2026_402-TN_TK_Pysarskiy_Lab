# Лабораторна робота №5

ASP.NET Core Identity зберігає користувачів і ролі в SQLite через GameContext. При запуску автоматично застосовуються міграції та створюються ролі Reader, Editor, Admin. GET персонажів і зброї доступний усім; POST і PUT — Editor або Admin; DELETE — Admin. Перегляд власного профілю `GET /api/users/me` доступний усім трьом ролям. Вбудовані `/identity/register` і `/identity/login` виконують реєстрацію і вхід; `/identity/login` повертає захищений Bearer-токен Identity (це не JWT).

При першому запуску встановіть змінні середовища `BootstrapAdmin__Email` та `BootstrapAdmin__Password` (надати власні значення), після чого виконайте `dotnet run --project Game.REST`. Початковий адміністратор створюється лише якщо роль Admin ще нікому не призначена; email не має належати наявному користувачу. Після ініціалізації видаліть ці змінні. Звичайна реєстрація не надає ролі автоматично: адміністратор призначає її через `POST /api/users/roles`, передаючи `{"email":"user@example.com","role":"Reader"}` та свій Bearer-токен. Дозволені ролі Reader, Editor та Admin. Після зміни ролі користувачу потрібно знову увійти, щоб отримати токен із новими правами.

Локальна перевірка на окремій копії бази: Lab5_report.pdf. Не публікуйте токени чи паролі. Використовуйте HTTPS, якщо API доступне за межами локального комп'ютера. Розгортання у хмарі (додаткове завдання) не виконано.
